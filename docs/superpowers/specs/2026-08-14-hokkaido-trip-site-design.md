# 北海道小旅行 — 行程網站設計

日期：2026-08-14
狀態：已與使用者確認，待撰寫實作計畫

## 1. 目標

把現有的設計原型 `design_handoff_hokkaido_trip/hokkaido-trip.html` 變成一個正式、可分享的網站，部署在 GitHub Pages。

兩個核心改變：

1. **行程資料改由 Google 試算表即時驅動**，不再手寫在程式碼裡。使用者改試算表，重整網頁就更新。
2. **從「行程檢視器」擴充成「旅遊網站」**，加上封面、總覽、城市、美食、照片牆等內容區塊。

行程本身：2026/12/25–12/31，旭川 → 小樽 → 洞爺 → 函館 → 札幌，7 天。1/1–1/3 尚未規劃，試算表中無資料。

## 2. 資料來源

### 2.1 試算表

- 網址：`https://docs.google.com/spreadsheets/d/1t0cg0bkqQLtyYYvFaGH7MlWoi4tHZGYhgTHnEWV90aU/export?format=csv&gid=0`
- 已實測回應 `Access-Control-Allow-Origin: *`，瀏覽器可跨網域直接讀取，不需代理。
- 欄位：`日期, 抵達時間, 城市, 地點, 活動內容, 交通工具, 交通時間, 費用清單C, 食物清單F`
- 現況：42 筆資料列、36 個相異地點。最後兩欄目前全空。

### 2.2 年份問題

試算表中日期為 `2025-12-25` 起，但使用者確認實際行程是 **2026** 年。星期幾必須由日期算出，因此**使用者需自行將試算表年份改為 2026**。程式不做年份覆寫——那會讓資料與顯示不一致，且日後無人記得。

若載入時偵測到行程日期早於今天，網頁在頁首顯示一行提示：「試算表日期看起來已過期，請確認年份」。

## 3. 資料模型推導

**核心洞察：試算表的每一列 = 一個景點 + 抵達該景點的那一段交通。**

因此路線不需另外維護：同一天內相鄰兩列即構成一段 leg。

```
leg[i] = {
  from:  row[i-1].地點,
  to:    row[i].地點,
  mode:  classify(row[i].交通工具),
  mins:  parseInt(row[i].交通時間),
  label: row[i].交通工具
}
```

當日第一列沒有前一列，故第一列只產生 spot、不產生 leg（跨日移動不畫線）。

### 3.1 交通方式分類

由「交通工具」欄以關鍵字判斷，決定路線顏色與載具圖示：

| 關鍵字 | mode | 顏色 |
|---|---|---|
| `JR`、`特急`、`特級`、`本線`、`Rapid Airport` | `jr` | `#0e7ad4` |
| `開車`、`租車` | `drive` | `#f4622e`（虛線） |
| `巴士`、`接駁車` | `bus` | `#12a97a` |
| `市電`、`地下鐵` | `tram` | `#f0ad2a` |
| `步行` | `walk` | `#f0ad2a` |
| 航班（如 `台灣虎航`） | `flight` | 不畫線 |
| 空值 / 無法判斷 | `walk` | 預設 |

判斷順序由上而下，先命中者為準（例如「Rapid Airport、JR 函館本線」同時含多個關鍵字，歸為 `jr`）。

`flight` 實務上只會出現在當日第一列（抵達北海道），而第一列不產生 leg，因此不會畫線；此分類僅用於卡片上顯示交通方式文字。

### 3.2 特殊列處理

- **地點為空**（如 `2025-12-30,18:00,函館市,,晚餐`）：不產生地圖標記，但在當日卡片列表中顯示為「待定」項目。
- **住宿判定**：「活動內容」含 `Check-in` 者標為住宿，使用紫色 `#7a5cc4`。
- **多地點欄位**（如 `大通公園、札幌電視塔`）：視為單一地點，座標取第一個。

## 4. places.json — 地名簿

試算表沒有座標，也沒有景點介紹。這些放在獨立的 `places.json`，以**地點名為 key**（與試算表的「地點」欄完全一致）。

```json
{
  "蜂屋 五条創業店": {
    "lng": 142.36400,
    "lat": 43.77000,
    "desc": "旭川拉麵的創業老店，焦香豬油的醬油湯頭配捲麵。",
    "photo": "photos/hachiya.jpg",
    "url": "https://..."
  }
}
```

- 現有 28 筆座標從原型的 `P` 物件搬過來，其餘 8 個地點需補齊。
- `desc` 從原型 `DAYS[].spots[].d` 搬過來。
- `photo` 對應原型的 `OWN` 對照表，18 張照片從 `uploads/` 搬到 `photos/` 並改成有意義的檔名。

### 4.1 未知地點的處理（不可當機）

試算表新增了地名簿沒有的地點時，依序：

1. 向 OpenStreetMap Nominatim 查詢座標，成功則使用，並快取於 `localStorage`（永久，除非使用者清除）。
   - 遵守 Nominatim 使用政策：每秒最多 1 次請求、帶 `User-Agent`／`Referer`。
2. 查詢失敗：該地點**照常出現在卡片列表**，只是不畫在地圖上。
3. 頁面顯示一則提示，列出所有無座標的地點名，方便使用者補進 `places.json`。

沒有 `desc` 的地點，卡片改顯示試算表的「活動內容」。

## 5. 頁面結構

由上而下：

| # | 區塊 | 內容 | 資料來源 |
|---|---|---|---|
| ⑨ | 導覽列 | 吸頂，跳至各區塊 | — |
| ① | 封面 Hero | 全幅大圖、標題、日期、五城市、出發倒數 D-xxx | 照片 + 試算表日期 |
| ② | 全行程總覽 | 7 天路線疊在同一張地圖；數字帶：天數／城市數／地點數／總移動距離 | 試算表 + places.json |
| ③ | 逐日行程 | **現有核心**：左側日期時間軸、右側動畫地圖、下方景點卡 | 試算表 + places.json |
| ④ | 五座城市 | 旭川／小樽／洞爺／函館／札幌，各一段介紹＋代表照片＋停留天數與造訪地點 | places.json + 城市文案 |
| ⑤ | 吃什麼 | 餐廳專區，主打「北海道拉麵三大天王」全中：旭川醬油（蜂屋）／函館鹽味（山崎洋服店）／札幌味噌（一粒庵）；其餘餐廳並列 | 試算表（「活動內容」含餐飲關鍵字者） |
| ⑧ | 照片牆 | 18 張照片瀑布流，點擊全螢幕檢視 | photos/ |

③ 完整沿用原型的互動與視覺，包含自動連播、載具沿路移動、抵達彈卡、下方卡片同步高亮。

### 5.1 城市分區對照（④）

試算表「城市」欄用的是行政區名，與網站要呈現的五座城市不一致，需明確對照：

| 試算表「城市」欄 | 網站城市區塊 |
|---|---|
| `旭川市` | 旭川 |
| `小樽市` | 小樽 |
| `虻田郡`、`有珠郡` | 洞爺 |
| `函館市` | 函館 |
| `札幌市` | 札幌 |
| `千歲市` | 不成區塊（僅為入境機場，歸入行程起點） |

此對照表寫在程式中。出現對照表以外的城市名時，自動以原字串新增一個區塊，不中斷渲染。

注意「札幌市」在行程中出現兩種角色：Day 1–3 只是轉車經過，Day 7 才是實際停留。城市區塊統計停留天數時，只計算當日有非轉車景點的日子（轉車判定：「活動內容」為 `轉車`）。

### 5.2 餐廳判定（⑤）

「活動內容」含 `早餐`／`午餐`／`晚餐`／`拉麵`／`定食` 等關鍵字者歸入美食區。拉麵三天王以 `places.json` 中的 `ramen` 標記（`醬油`／`鹽味`／`味噌`）明確指定，不靠字串猜測。

### 5.3 總移動距離（②）

由各 leg 兩端座標以 haversine 累加。這是直線距離的總和，非實際里程，畫面上標示為「約」。

## 7. 技術與部署

### 7.1 結構

單頁靜態網站，無框架、無 build step。

```
index.html      版面與樣式
app.js          抓取 → 解析 → 建模 → 渲染
places.json     地名簿
photos/         景點照片
```

外部依賴：Leaflet（地圖）、OpenStreetMap 圖磚、OSRM demo（道路路徑）、Nominatim（未知地點地理編碼）。

### 7.2 錯誤處理

| 失敗情境 | 行為 |
|---|---|
| 試算表抓取失敗 | 顯示錯誤訊息與重試按鈕，並說明可能原因（試算表未公開／離線） |
| OSRM 無回應或逾時 | 退回原型既有的平滑折線（Catmull-Rom），路線變近似曲線但不中斷 |
| Nominatim 查無座標 | 該地點不上地圖，卡片照常顯示，頁面列出待補清單 |
| 照片缺失 | 顯示佔位底色，不破版 |

OSRM demo 與 Nominatim 皆為公共服務、無服務保證。兩者都必須有退路，且退路不得阻塞畫面渲染。

### 7.3 部署

`git init` → 推上 GitHub → 開啟 GitHub Pages（`main` 分支根目錄）。網站為純靜態檔案，無需建置流程。

必須保留 OpenStreetMap 的 attribution。

### 7.4 交付階段

分兩階段，第一階段結束時網站即可上線運作：

- **階段一 — 核心可用**：試算表驅動的資料層、`places.json`、③ 逐日行程（沿用原型互動）、部署上線。
- **階段二 — 內容區塊**：⑨ 導覽列、① 封面、② 總覽、④ 五座城市、⑤ 吃什麼、⑧ 照片牆。

## 8. 不做的事

- 不做即時電車時刻表查詢（需付費 API，且資料易過期）
- 不做匯率換算、留言板
- 不做後端、不做使用者帳號
- 不把年份錯誤在程式裡硬改
- 「費用清單C」「食物清單F」兩欄本次不實作視覺化；欄位保留，有資料時不報錯即可

## 1. 目標

### 2.2 敏感欄位（必須遵守）

網站部署於公開網址。以下欄位**永不渲染到畫面，也不寫入任何前端可讀的資料結構**：

- 交通頁籤的 `訂位 / 備註`（含訂位代號，例如 PNR）
- 住宿頁籤的 `備註` 中若含訂房編號

實作方式為欄位白名單：明確列出要讀取的欄位，而非讀取全部後再排除。新增欄位時預設不顯示，避免日後有人在試算表加了敏感欄位而意外外洩。

理由：訂位代號加上乘客姓氏，在多數航空公司系統中足以查詢甚至變更訂位。

### 2.3 日期年份不一致

使用者已將「行程規劃」頁籤的年份改為 2026，但**其餘四個含日期的頁籤仍為 2025**（餐飲、住宿、交通、費用規劃）。

網站不做年份覆寫——那會讓資料與顯示不一致。改為：跨頁籤以日期關聯資料時，只比對**月-日**，忽略年份。並在載入後若偵測到頁籤間年份不一致，於畫面顯示一則提示。

## 3. 行程資料模型（gid=0）

**核心洞察：每一列 = 一個景點 + 抵達該景點的那一段交通。**

因此路線不需另外維護：同一天內相鄰兩列即構成一段 leg。

```
leg[i] = {
  from:  row[i-1].地點,
  to:    row[i].地點,
  mode:  classify(row[i].交通工具),
  mins:  parseInt(row[i].交通時間),
  label: row[i].交通工具
}
```

當日第一列沒有前一列，故只產生 spot、不產生 leg（跨日移動不畫線）。

### 3.1 交通方式分類

| 關鍵字 | mode | 顏色 |
|---|---|---|
| `JR`、`特急`、`特級`、`本線`、`Rapid Airport` | `jr` | `#0e7ad4` |
| `開車`、`租車` | `drive` | `#f4622e`（虛線） |
| `巴士`、`接駁車` | `bus` | `#12a97a` |
| `市電`、`地下鐵` | `tram` | `#f0ad2a` |
| `步行` | `walk` | `#f0ad2a` |
| 航班（如 `台灣虎航`） | `flight` | 不畫線 |
| 空值 / 無法判斷 | `walk` | 預設 |

判斷順序由上而下，先命中者為準（「Rapid Airport、JR 函館本線」歸為 `jr`）。

`flight` 實務上只出現在當日第一列，而第一列不產生 leg，因此不會畫線；此分類僅用於卡片顯示交通方式文字。

### 3.2 特殊列處理

- **地點為空**（如 `12/30 18:00 函館市 (空) 晚餐`）：不產生地圖標記，在當日卡片列表顯示為「待定」。
- **住宿判定**：「活動內容」含 `Check-in`。
- **多地點欄位**（如 `大通公園、札幌電視塔`）：視為單一地點，座標取第一個。

## 4. places.json — 地名簿

試算表沒有座標與景點介紹，這些放在獨立的 `places.json`，以**地點名為 key**（與「行程規劃」頁籤的「地點」欄完全一致）。

```json
{
  "蜂屋 五条創業店": {
    "lng": 142.36400,
    "lat": 43.77000,
    "desc": "旭川拉麵的創業老店，焦香豬油的醬油湯頭配捲麵。",
    "photo": "photos/hachiya.jpg",
    "ramen": "醬油"
  }
}
```

- 現有 28 筆座標從原型的 `P` 物件搬過來，其餘 8 個地點需補齊。
- `desc` 從原型 `DAYS[].spots[].d` 搬過來。
- `photo` 對應原型的 `OWN` 對照表，18 張照片從 `uploads/` 搬到 `photos/` 並改為有意義的檔名。

### 4.1 未知地點的處理（不可當機）

1. 向 OpenStreetMap Nominatim 查詢座標，成功則使用並快取於 `localStorage`。遵守其使用政策：每秒至多 1 次請求。
2. 查詢失敗：該地點**照常出現在卡片列表**，只是不畫在地圖上。
3. 頁面顯示提示，列出所有無座標的地點名，方便補進 `places.json`。

沒有 `desc` 的地點，卡片改顯示試算表的「活動內容」。

### 5.1 全站只有一張地圖（②③ 合併）

原型的 `buildBase()` 已將**所有日期的路線**以灰線（`#9aa0a6`, weight 2, opacity .4）常駐畫在逐日地圖上。若 ② 再放一張全行程地圖，兩者呈現的是同一組路線、只差顏色，且兩區塊上下相鄰——這是結構性重複，不只是視覺重複。

因此**全站只建立一個 Leaflet 實體**，位於 ③。

- ③ 左側日期時間軸新增第一列「**全程**」。選取時：七天路線各自以當日交通色上色（取代灰色底圖）、`fitBounds` 到全程範圍、不播放動畫、不顯示載具。
- 「全程」為**載入後的預設畫面**。停留約 2.6 秒後（與現有自動連播的間隔一致）自動進入 Day 1 開始連播。使用者點任一日期即停止自動連播，行為與原型相同。
- ② 區塊保留標題、敘述與數字帶，並保留每日色彩圖例（作為 ③ 的閱讀索引）。

好處：一套互動邏輯、少一個 Leaflet 實體與一份圖磚流量，且「先看全貌再進入細節」的開場比原型直接跳進 Day 1 更順。

### 5.2 城市分區對照（④）

「城市」欄是行政區名，與要呈現的五座城市不一致，需明確對照：

| 試算表「城市」欄 | 網站城市區塊 |
|---|---|
| `旭川市` | 旭川 |
| `小樽市` | 小樽 |
| `虻田郡`、`有珠郡` | 洞爺 |
| `函館市` | 函館 |
| `札幌市` | 札幌 |
| `千歲市` | 不成區塊（入境機場） |

此對照表寫在程式中。出現對照表以外的城市名時，自動以原字串新增一個區塊，不中斷渲染。

「札幌市」有雙重角色：Day 1–3 只是轉車經過，Day 7 起才實際停留。統計停留天數時只計算當日有非轉車景點的日子（轉車判定：「活動內容」為 `轉車`）。

### 5.3 餐廳與拉麵三天王（⑤）

餐廳直接讀「餐飲」頁籤，不從「活動內容」猜測。拉麵流派以 `places.json` 的 `ramen` 欄明確指定（`醬油`／`鹽味`／`味噌`），不靠字串比對。

### 5.4 住宿晚數（⑥）

「住宿」頁籤有入住日與退房日，晚數由兩者相減得出。該頁籤只填了前三間；函館與札幌需由「待辦清單」頁籤的項目名稱補足日期區間，費用顯示為「待補」。

### 5.5 費用與幣別（⑦）

「費用規劃」頁籤同時使用 NTD 與 JPY 兩欄，同一列只會填其中一欄。

- 統一換算為台幣後合計：`twd = NTD + JPY × RATE`
- `RATE` 寫在設定檔（初值 `0.21`），使用者可自行調整。**不串接即時匯率 API**——多一個會壞的外部依賴，而匯率精度對估算無實質影響。
- 明細列同時顯示換算後台幣與原始日圓金額。

**誠實呈現未完成資料**：13 個項目中僅 7 項有金額。畫面標示為「**已登錄總額**」而非「總預算」，並同時顯示「7 / 13 項」，避免把低估值誤讀為完整預算。未填項目顯示「待補」而非 0。

### 5.6 總移動距離（②）

由各 leg 兩端座標以 haversine 累加，為直線距離總和而非實際里程，畫面標示為「約」。

## 7. 技術與部署

### 7.1 結構

單頁靜態網站，無框架、無 build step。

```
index.html      版面與樣式
app.js          抓取 → 解析 → 建模 → 渲染
config.js       匯率、試算表 ID、各頁籤 GID
places.json     地名簿
photos/         景點照片
```

外部依賴：Leaflet、OpenStreetMap 圖磚、OSRM demo（道路路徑）、Nominatim（未知地點地理編碼）。

**全站只建立一個 Leaflet 實體**（見 5.1）。

六個頁籤並行抓取，任一頁籤失敗只讓對應區塊顯示錯誤，不影響其他區塊。

### 7.2 錯誤處理

| 失敗情境 | 行為 |
|---|---|
| 某頁籤抓取失敗 | 該區塊顯示錯誤與重試按鈕，其餘區塊照常 |
| 全部抓取失敗 | 顯示錯誤與可能原因（試算表未公開／離線） |
| OSRM 無回應或逾時 | 退回原型既有的平滑折線，路線變近似曲線但不中斷 |
| Nominatim 查無座標 | 該地點不上地圖，卡片照常顯示，頁面列出待補清單 |
| 照片缺失 | 顯示佔位底色，不破版 |
| 金額欄為空 | 顯示「待補」，不計入總額，不顯示為 0 |

OSRM demo 與 Nominatim 皆為公共服務、無服務保證，兩者的退路都不得阻塞畫面渲染。

### 7.3 部署

`git init` → 推上 GitHub → 開啟 GitHub Pages（`main` 分支根目錄）。純靜態，無需建置流程。必須保留 OpenStreetMap attribution。

### 7.4 交付階段

- **階段一 — 核心可用**：資料層（六頁籤抓取與解析）、`places.json`、③ 逐日行程、部署上線。
- **階段二 — 內容區塊**：⑨ 導覽列、① 封面、② 總覽、④ 五座城市、⑤ 吃什麼、⑥ 住哪裡、⑦ 花多少、⑩ 行前準備。

## 8. 已知資料落差

這些是試算表本身的問題，網站**如實呈現、不隱藏也不自行修正**。列此供使用者決定是否修改資料：

1. **年份不一致**——僅「行程規劃」改為 2026，其餘四個頁籤仍為 2025。
2. **行程只填了 7 天 / 10 天**——1/1–1/2 尚未規劃，但機票住宿已訂妥。
3. **人數不一致**——機票備註為三人份行李，JR Pass（¥28,000/位 → ¥56,000）與 ICOCA（¥4,000/位 → ¥8,000）皆為兩人份。
4. **成吉思汗店名不一致**——「費用規劃」寫旭川分店，「餐飲」與「待辦清單」皆寫函館五稜郭店，行程為 12/30 在函館。
5. **住宿頁籤缺兩間**——函館與札幌未填，但待辦清單顯示已訂房。
6. **照片對照表兩筆對不上**——`成吉思汗大黑屋 五稜郭店` vs 表中 `成吉思汗大黑屋 函館五稜郭店`；`薄野 民宿 IK1003` vs 表中 `Downtown area Spacious cozy room Susukino IK901`。以地點名為 key 的查表會漏掉這兩張照片，需在 `places.json` 建立別名。

## 9. 不做的事

- 不做照片牆
- 不串接即時匯率 API
- 不做即時電車時刻表查詢（需付費 API，資料易過期）
- 不做留言板、後端、使用者帳號
- 不在程式裡硬改試算表的資料錯誤
- 不顯示訂位代號等敏感欄位

## Context

專案目前有一份高完成度的設計原型 `design_handoff_hokkaido_trip/hokkaido-trip.html`：Leaflet 地圖、日期時間軸、單日動畫播放、景點卡片，視覺與互動皆為最終品質。但行程資料（`DAYS`、`P`、`VIA`、`LEG_SPOT`、`OWN`、`WIKI`）全部手寫在該檔案中。

真正的資料來源是一份 Google 試算表的六個頁籤：行程規劃（42 列）、餐飲、住宿、交通、費用規劃、待辦清單。這六個頁籤彼此有關聯（同一間餐廳同時出現在行程規劃、餐飲與費用規劃），但目前無法一起閱讀。

行程為 2026/12/25 – 2027/01/03，出發前仍有數個月，資料會持續變動。使用者已選定：GitHub Pages 公開部署、資料每次開頁即時抓取。

**既有限制**

- 試算表為單一事實來源；網站不得寫回，也不得在程式中修正其資料錯誤
- 部署為公開網址，而交通頁籤含訂位代號
- 行程跨越年界（2026/12/25 – 2027/01/03），日期處理必須正確跨年
- 試算表沒有座標，也沒有景點介紹文字

## Goals / Non-Goals

**Goals:**

- 使用者改試算表、重整網頁即更新，不需要碰程式碼
- 沿用原型的視覺與地圖互動，達到像素級一致
- 任何一項外部服務或資料欄位失效，都只降級不崩潰
- 敏感欄位不可能意外外洩，即使日後有人在試算表新增欄位
- 資料的不完整與矛盾在畫面上看得見，而非被靜默掩蓋

**Non-Goals:**

- 不做後端、資料庫、使用者帳號
- 不做建置流程（無打包器、無框架）
- 不寫回試算表，網站為唯讀
- 不串接即時匯率或電車時刻表 API
- 不做照片牆
- 不在程式中修正試算表的資料錯誤

## Decisions

### 決策一：每列即「景點 + 抵達它的交通」，路線由相鄰列推導

「行程規劃」頁籤的每一列都有「地點」「抵達時間」「交通工具」「交通時間」。觀察後可確認：交通工具描述的是**抵達本列地點**所搭乘的工具。因此同一天內相鄰兩列即構成一段路線。

**替代方案**：在試算表另開一個「路線」頁籤手動維護每段起訖。**否決理由**：與行程規劃頁籤重複，且兩者一旦不同步就會產生錯誤路線。現行推導方式讓使用者只需維護一份資料。

**代價**：跨日的移動不畫線（當日第一列沒有前一列）。實務上跨日移動就是隔夜住宿，本來就不該畫線，因此代價為零。

### 決策二：座標與介紹放在 `places.json`，未知地點即時地理編碼

試算表沒有座標，但地圖需要。

**替代方案 A**：在試算表新增「座標」欄由使用者填寫。**否決理由**：每加一個地點就要去查經緯度，維護負擔直接落在使用者身上。

**替代方案 B**：全部即時地理編碼。**否決理由**：Nominatim 有速率限制且對日文店名的解析品質不穩，36 個地點每次開頁都查會既慢又不可靠。

**採用**：兩層設計。已知的 36 個地點寫入 `places.json`（座標、介紹、照片、拉麵流派、別名）；試算表新增的未知地點才即時查 Nominatim，查得後快取於 `localStorage`，查不到則該地點仍出現在卡片列表、只是不上地圖，並在畫面列出待補清單。

這讓「即時同步」是真的即時——臨時加一家餐廳到表裡，重整就會出現。

### 決策三：欄位白名單而非黑名單

交通頁籤含訂位代號，網站部署於公開網址。

**替代方案**：把敏感欄位列入黑名單排除。**否決理由**：黑名單是「預設顯示」，日後在試算表新增任何欄位都會自動外洩，且沒有人會記得回來更新黑名單。

**採用**：解析時只讀取明確列舉的欄位。新增欄位預設不顯示，需要顯示才主動加入白名單。安全性的預設值應該是保守的。

### 決策四：全站只有一個 Leaflet 實體

原型的 `buildBase()` 已將所有日期的路線以灰線常駐畫在逐日地圖上。原先規劃的「全行程總覽」區塊若另設一張地圖，兩者呈現的是同一組路線、只差顏色，且兩區塊上下相鄰——這是結構性重複。

**採用**：「全程」成為日期時間軸的第一列，也是載入後的預設畫面；選取時七天路線各自上色。總覽區塊保留數字帶與色彩圖例，不再擁有地圖。

**額外好處**：少一個 Leaflet 實體與一份圖磚流量；且「先看全貌再進入細節」的開場比原型直接跳進 Day 1 更順。

### 決策五：以完整日期排序，月-日僅作為關聯的退路

六個頁籤的年份原本不一致（僅「行程規劃」更新為 2026），使用者已於規格撰寫後全數修正為 2026。

**替代方案 A**：在程式中把年份一律正規化。**否決理由**：等於偷改使用者的資料，且會掩蓋真正的輸入錯誤。

**替代方案 B**：一律只比對月-日。**否決理由**：本行程跨越年界（2026/12/25 – 2027/01/03），只比對月-日會讓 `01-01` 排在 `12-25` 之前，產生嚴重的排序錯誤。

**採用**：排序與關聯皆以完整日期為準；完整日期找不到對應時才退回月-日比對並顯示年份不一致提示。此外，當某列日期早於行程起始日時顯示異常提示——使用者很可能把 1/1 填成 `2026-01-01` 而非 `2027-01-01`，這個提示能讓錯誤立刻現形。

### 決策六：匯率寫在設定檔，不串接 API

「費用規劃」頁籤同時使用 NTD 與 JPY 兩欄，需統一換算才能合計。

**替代方案**：串接即時匯率 API。**否決理由**：多一個會失效的外部依賴，而匯率精度對「這趟大概要花多少」的估算沒有實質影響。

**採用**：匯率寫在 `config.js`，使用者可自行調整，畫面上明示目前使用的匯率。

### 決策七：區分「已登錄總額」與「總預算」

13 個費用項目中僅 7 項有金額，且函館與札幌的住宿根本沒列進費用頁籤。

若直接顯示「總預算 NT$114,730」，使用者會誤以為錢已經算完。**採用**：標籤為「已登錄總額」，並同時顯示「7 / 13 項」；未填項目顯示「待補」而非 0。這是整份設計的一貫原則——資料的不完整必須看得見。

### 決策八：無框架、無建置流程

網站規模為單頁、八個區塊、一個資料層。

**替代方案**：Vite + React。**否決理由**：引入建置流程後，使用者要更新網站就必須具備 Node 環境並執行建置，與「改試算表就更新」的目標相衝突；且原型的地圖互動是直接操作 Leaflet 的命令式程式碼，包進 React 反而增加阻抗。

**採用**：`index.html` + `app.js` + `config.js` + `places.json`，直接部署，無中間步驟。

## Risks / Trade-offs

**OSRM demo 無服務保證** → 該服務僅用於自駕、巴士、步行與市電的實際道路路徑。失敗時退回原型既有的平滑折線，路線變成近似曲線但功能不中斷。退路不得阻塞畫面渲染。

**Nominatim 有速率限制與使用政策** → 僅用於 `places.json` 未涵蓋的地點，並限制每秒至多一次請求、結果快取於 `localStorage`。已知的 36 個地點完全不觸發此路徑，因此正常使用下幾乎不會呼叫。

**試算表必須保持公開** → 一旦改為非公開，網站將無法讀取。抓取失敗時顯示明確錯誤與可能原因，讓使用者知道要去檢查分享設定。

**總移動距離為直線累加** → 以 haversine 計算，非實際搭乘里程，會低估。畫面標示「約」以表明其性質。

**新增地點在補上 `desc` 之前只有簡短文字** → 卡片改顯示試算表的「活動內容」，仍可閱讀，只是不如既有地點豐富。

**照片對照表有兩筆與試算表命名不符** → `成吉思汗大黑屋 五稜郭店` 對應表中 `成吉思汗大黑屋 函館五稜郭店`；`薄野 民宿 IK1003` 對應表中 `Downtown area Spacious cozy room Susukino IK901`。以 `places.json` 的別名機制解決。

**試算表資料本身有六項落差** → 網站如實呈現而不自行修正。這些落差已記錄於 proposal 的 Impact 一節，由使用者決定是否修改資料。

## Migration Plan

專案目前不存在生產環境網站，因此無資料遷移或回滾需求。

1. **階段一 — 核心可用**：建立 `config.js` 與資料層（六頁籤抓取、解析、白名單）、由原型搬出 `places.json`、實作單一地圖與逐日行程、部署至 GitHub Pages。此階段結束時網站即可運作。
2. **階段二 — 內容區塊**：導覽列、封面、總覽、五座城市、吃什麼、住哪裡、花多少、行前準備。

原型 `design_handoff_hokkaido_trip/` 保留為設計參考，不刪除。
